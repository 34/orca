## 分支与版本策略（建议）

建议 `main` 保存经过验证的官方稳定源码集成，`34/local` 保存官方源码加本地定制功能。需求中的 local 对应当前实际分支 `34/local`，无需再创建同义分支。

流程：官方 release tag → 临时上游同步分支 → fork main；再将该 main 的固定提交 → 临时定制集成分支 → 34/local → 构建 Orca 34。

首次必须检查当前 main 与稳定 tag 的祖先关系。现有基线可能包含比稳定分支更新的开发提交，不能按版本号直接 reset、强推或假定可快进。非祖先情况下保留历史合并，并核验 runtime/daemon 等必要能力；若最终决定 main 要成为纯官方镜像，另作显式迁移，不能在自动任务里重写。

两个目标先在临时分支完成集成验证，再依次推进长期分支；记录推进点。main 已推进而 local 失败时，保留旧已发布版本，从记录恢复 local 集成，不自动回退公共分支。分支推进和安装成功分别记账，不能合并为一个“已升级”状态。

版本清单记录：官方 tag 与解析 SHA、fork 源码 SHA、应用版本、架构、依赖锁文件摘要、产物 SHA-256、签名模式、检查链接、构建时间。使用独立 fork 版本递增规则，不覆盖官方 tag，不只依赖 package.json 的旧版本号。

## 自动流程

| 阶段     | 行为与门禁                                                                                          | 失败后的处理                                                    |
| -------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 发现     | 建议每 6 小时检查官方正式桌面 release，排除草稿/预发布；缓存请求与已处理 tag/SHA                    | 网络错误退避；同 tag 换 SHA 停止自动推进并报告                  |
| 准备     | 固定目标 tag/SHA、基线和目标分支 SHA；检查干净源码、磁盘、工具链；每条发布线只运行一个任务          | 不 stash/reset 用户改动；繁忙时等待，不并发构建或安装           |
| 合并     | 临时分支合并官方内容，再合入定制内容；记录每个冲突及解决理由                                        | 保留可继续的失败分支；禁止整库 ours/theirs、删测试或弱化门禁    |
| 修复     | Agent 阅读双方意图，解决冲突及相关回归；建议最多 3 轮有效修复                                       | 无法确认语义、安全/数据迁移问题或重复失败时停止发布并给出阻塞项 |
| 验证     | 定向测试、类型与质量检查、完整 PR workflow；检查 workflow 身份、required checks、verify 和精确 head | pending/失败/缺失均不允许推进；head 改变重新核验                |
| 构建     | 从已验证的固定源码构建，复用现有脚本；干净产物目录、独立身份、签名/清单/真实 PTY 检查               | 不复用残留旧包；保留日志和失败身份                              |
| 发布准备 | 本地版本目录保存包、校验和、变更摘要及兼容说明；用隔离 profile 跑旧→新→旧回归                       | 候选失败不移动“可安装版本”指针                                  |
| 安装     | 核验无本实例运行任务与数据写入者，备份旧包和实际 profile；同卷暂存并替换；健康检查                  | 活跃会话不强制关闭；标记待安装，等待空闲窗口                    |
| 回退     | 新版本失败时停止本实例写入，保留升级后数据，恢复旧包和配套备份                                      | 用户已有新工作时不自动覆盖其数据；保留两份并报告恢复方案        |
| 收尾     | 分别记录源码集成、产物就绪、安装版本和健康结果；仅状态有实质变化时通知                              | 重启后从阶段回执恢复，不重复发布或覆盖安装                      |

自动解决冲突是自动尝试并验证，不是保证任意冲突都可安全无人值守。源码无冲突也可能有行为回归，仍需完整验证。CI 通过不能代替数据迁移与安装健康检查。

“本地发布”首先定义为在本机保存可安装包和清单；公开 GitHub Release、自动更新 feed 是单独的发布目标。第一阶段不必为了本机升级先开发公网更新服务。当前 Orca 34 的官方更新 feed 禁用状态继续保留；将来使用 fork feed 时必须验证包身份、版本顺序和签名。

## 自动任务的运行方式

第一步把每个阶段实现为可手动运行、可恢复、可诊断的命令，再接调度器。定时器只触发和恢复流程，不成为唯一保存状态的位置。状态记录放在持久的 fork 发布数据目录，不依赖当前聊天或可清理的 `.context`。

建议先启用“只发现并生成候选 PR/包”模式，完整跑通一次 v1.4.232 集成和升级演练后，再启用“检查通过自动合并、空闲时安装”。发布权限使用最小仓库范围，不复用上游官方发布凭据；不启用所有继承的上游发布工作流。

本机关闭或离线会延迟本地调度；若需要全天发现，可让 GitHub 负责发现与 PR 检查，本机承担 macOS 构建和安装。不得把公共仓库任意 PR 代码直接送到有私人数据和签名凭据的本机 runner。

计划阶段尚不创建定时任务。启用时再把运行频率、自动推进模式及安装空闲条件写入实际配置。

## 实施拆分与验收

1. **交付 A：可靠本地升级。** 将现有构建与安装步骤变为统一入口，新增升级状态记录，完成当前日常版到最新功能候选的升级/回退演练。覆盖运行中延迟、备份失败、替换中断、健康检查失败；确认真实任务目录与分支未被改写。
2. **交付 B：首次官方同步。** 核验 v1.4.232 与基线差异，保留定制功能解决冲突，跑完整 PR 检查，生成可追溯候选。此阶段证明同步机制，不用更改文档中的版本号代替实际合并。
3. **交付 C：自动编排。** 加发现、去重、持久回执、互斥、有限修复与通知；覆盖重复触发、离线、进程重启、CI head 变化、main/local 部分推进及安装失败。
4. **交付 D：日常 Agent 完整性。** Cursor 根工作区实机运行与停止/恢复；明确 Skills/插件实际作用范围，并补工作区覆盖配置。
5. **交付 E：持续体验优化。** 根据实际任务积累补管理筛选、默认组合及附件操作，不在发布基础未闭环时扩展大量面板。

每个交付提供用户可复核的结果、失败记录和恢复方式。UI 以隐藏 CDP 为常规回归；原生 computer use 使用隔离候选和明确授权的可见窗口，不把本轮可见窗口例外扩大为长期随时抢焦点的许可。
